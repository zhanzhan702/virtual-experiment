# 个人消息管理（自助改密） — 设计

日期：2026年09月10日
状态：待实现
依赖：Phase 0/1（JWT 鉴权、后台布局）已完成

## 一、背景与范围

管理后台 5 个功能中的第 5 个，也是最小的一个：让用户修改**自己的**密码。

### 解决的问题

此前密码只能由**管理员替他人**重置（`PUT /api/admin/users/{id}/password`），没有自助入口。由此带来两个实际困扰：

1. **`superadmin` 的密码无法修改** —— 它的初始哈希与 `admin` 相同（见 `02_create_data.sql`），而管理员重置接口的规则是「目标 level < 我的 level」，超管看不到同级或更高，因此**连自己都改不了**
2. 教师、管理员想换密码只能找另一个管理员代劳

### 与「重置他人密码」的区别

| | 重置他人（已有） | 自助改密（本次） |
| --- | --- | --- |
| 路径 | `PUT /api/admin/users/{id}/password` | `PUT /api/auth/password` |
| 门槛 | `@RequireRole(TEACHER)` + 层级校验 | 仅需登录 |
| 验证原密码 | 不需要（管理员不知道对方密码） | **必须验证** |
| 目标 | 由路径参数指定 | 恒为当前登录用户 |

### 本期不做

- 学生端入口（学生实验页暂无合适位置，接口已具备，后续可在学生端加一个弹窗复用）
- 修改姓名、电话、邮箱等个人资料
- 忘记密码 / 邮箱或短信找回
- 会话管理（查看登录设备、踢出其他会话）

## 二、三项关键决定

### 2.1 必须验证原密码

改密是高危操作。若不验证原密码，**任何拿到 token 的人都能改掉密码，把真正的主人锁在系统外**。原密码是会话被盗用时的最后一道防线。

服务端用 `BCryptPasswordEncoder.matches(原密码, 库中哈希)` 校验，失败返回 400 `原密码不正确`。

### 2.2 改密成功后强制重新登录

前端在收到成功后：清 `localStorage.token` → 重置 authStore → 跳转登录页，并提示「密码已修改，请用新密码登录」。

这样做有两个好处：用户能**立即验证**新密码可用；符合用户对改密行为的常规预期。

**不需要后端改动** —— JWT 是无状态的，前端清掉 token 即完成登出。

### 2.3 新密码不得与原密码相同

改成一个和原来一样的密码没有意义，且会让用户误以为已生效。服务端用同一个 `matches` 再校验一次，相同则返回 400 `新密码不能与原密码相同`。

## 三、后端设计

### 3.1 接口

```
PUT /api/auth/password
（不在免鉴权白名单中，需登录；无 @RequireRole —— 任何登录用户都能改自己的密码）

请求体：
{
  "oldPassword":     "旧密码",
  "newPassword":     "新密码",
  "confirmPassword": "新密码"
}

成功 → 200 {"message": "密码修改成功"}
失败 → 400 {"message": "..."}   （具体文案见 3.2）
```

放在 `AuthController` 而非新建控制器：它是所有登录用户的通用能力，与 `/api/auth/me` 同类。`SecurityWhitelist` 已按精确路径放行 `login` / `register`，本接口自动需要登录，无需改动白名单。

### 3.2 校验顺序

分两个阶段，任一不满足即返回 400：

**阶段一 —— Bean Validation（DTO 注解，进入 Service 之前）**

| 校验 | 失败响应 |
| --- | --- |
| 三个字段均非空 | `密码不能为空` / `请再次输入新密码` / `请输入原密码` |
| 新密码满足强度规则（与注册、重置他人密码共用同一正则） | `密码需6-20位，且同时包含字母和数字` |

**阶段二 —— Service 内**

| 顺序 | 校验 | 失败响应 |
| --- | --- | --- |
| 1 | 两次输入的新密码一致 | `两次输入的密码不一致` |
| 2 | 原密码正确（BCrypt 比对） | `原密码不正确` |
| 3 | 新密码不同于原密码 | `新密码不能与原密码相同` |

**顺序有讲究**：格式类校验全部前置，**涉及查库与 BCrypt 比对的放在最后**。BCrypt 是刻意设计成慢的（防暴力破解），让格式错误的请求先被挡掉，可以避免无谓的计算开销。

### 3.3 新旧字段命名

已有 `dto/admin/UpdatePasswordDTO`（管理员重置他人，两个字段）。本次新增 `dto/auth/ChangePasswordDTO`（三个字段，多一个 `oldPassword`）。

**刻意不合并两者**：它们的语义不同（一个是「我改我自己」，一个是「管理员改别人」），且管理员重置接口不应接受 `oldPassword` 字段。合并会让两个场景互相牵制。

### 3.4 后端改动清单

| 文件 | 动作 |
| --- | --- |
| `dto/auth/ChangePasswordDTO.java` | 新增 |
| `service/UserService.java` + `impl/UserServiceImpl.java` | 修改：新增 `changePassword(userId, dto)` |
| `controller/AuthController.java` | 修改：新增 `PUT /password` |

`BCryptPasswordEncoder` 在 `UserServiceImpl` 已有实例，直接复用。

## 四、前端设计

### 4.1 文件结构

```
frontend/src/
├── views/Admin/ProfileView.vue     改密表单页
└── api/auth.js                     修改：新增 changePassword()
```

路由新增 `/admin/profile`，顶栏「个人消息管理」的 `disabled` 改为 `false`。该页门槛为教师（`minLevel: 20`，继承自父路由），所有能进后台的角色都可用。

### 4.2 表单

```
┌──────────────────────────────────┐
│  修改密码                          │
│                                    │
│  原密码    [________________]      │
│  新密码    [________________]      │
│           6-20位，含字母和数字      │
│  确认密码  [________________]      │
│                                    │
│  [确认修改]                        │
└──────────────────────────────────┘
```

三个输入框均 `show-password`。前端做即时校验（两次一致 + 强度规则，复用 `@/constants/password-rule`），提交按钮在有未填项时置灰。

**前端校验只是即时反馈，服务端才是权威** —— 原密码是否正确只有服务端知道。

### 4.3 成功后的处理

```js
await changePassword({ oldPassword, newPassword, confirmPassword })
ElMessage.success('密码已修改，请用新密码登录')
authStore.clearAuth()
router.push('/')
```

页面用 `el-card` 限宽居中，与其他后台页面的卡片风格保持一致。

## 五、验证方式

**准备**：测试账号 `gen_s2`（备份其密码哈希，测完还原）。

1. 用 `admin` 登录 → 进入「个人消息管理」→ 原密码填错 → 400 `原密码不正确`
2. 新密码填 `123456`（纯数字）→ 400 强度不足
3. 两次新密码不一致 → 400
4. 新密码与原密码相同 → 400 `新密码不能与原密码相同`
5. 全部正确 → 200；**前端跳回登录页**
6. 用**新密码**登录 → 成功
7. 用**旧密码**登录 → 失败
8. 改密后原 token 仍有效（JWT 无状态的预期行为，验证接口不依赖会话状态）
9. 未登录直接调 `PUT /api/auth/password` → 401
10. 学生登录后调该接口 → 200（所有登录用户都有权改自己的密码）
11. `superadmin` 能改自己的密码（**本次要解决的核心问题**）

## 六、待确认风险

| 风险 | 说明 | 处置 |
| --- | --- | --- |
| 原密码可被暴力破解 | 接口无失败次数限制，理论上可反复试错 | 本期不做。内网教学系统风险可接受；若要加，应是全局的 IP 限流而非本接口独有 |
| 改密不失效其他会话 | 无 `token_version`，用同一账号在别处登录的会话仍有效 | 与管理员重置密码的取舍一致，已确认接受 |
| 与重置接口的规则不一致 | 管理员重置不验证原密码、不强制重新登录 | 刻意如此：管理员本就不知道对方密码；被重置的人下次登录自然用新密码 |
| `superadmin` 初始密码仍等于 `admin` | 本次只是**让它可以被改**，并不会自动改掉 | 上线后应提示用户尽快自行修改 |
